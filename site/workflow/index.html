How inkmesh works

One program on your server, behind your own subdomain. People in the browser and AI agents through MCP or the API all go through the same code, which writes Markdown files to git repositories and keeps everything else in one SQLite file.

Life of a document

An agent drops a weekly report, a client reads it, a teammate fixes a paragraph, and the agent picks up the feedback.

  1. Claude Code calls create_document through MCP.
  2. The core checks that Jon, who connected the agent, is an editor or owner of the workspace.
  3. The file is written to workspaces/studio/reports/weekly.md.
  4. Git commits it at once, with the author “Jon via claude-code”.
  5. An event lands in the members’ inbox, and in the daily email of those who turned it on.
  6. Your client opens the page in the browser, with an account or a public link.
  7. A teammate edits a paragraph; the editor saves two seconds after the last keystroke.
  8. The editing session becomes one commit when they leave, after a minute idle, or when someone else writes the file.
  9. On its next run, the agent reads the comments left on the page with read_comments.

What lives where

One data directory holds it all. Copy it and you have a backup.

The database

Accounts, sessions, roles, invitations, agent tokens (stored hashed), public links and events. Also the search index, rebuilt from the files at every start.

inkmesh.db

The git repositories

One per workspace: the Markdown files, their images, and the comment threads in .inkmesh/comments/. You can clone and read them without inkmesh.

workspaces/<slug>/

What leaves the server

Email through your own SMTP server, only if you set one. The optional backup script pushes each workspace to a private GitHub repository. No analytics.
