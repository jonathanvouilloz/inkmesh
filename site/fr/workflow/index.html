Comment fonctionne inkmesh

Un seul programme sur votre serveur, derrière votre propre sous-domaine. Les personnes dans le navigateur et les agents IA via MCP ou l’API passent par le même code. Il écrit les documents en fichiers Markdown dans des dépôts git et garde tout le reste dans un fichier SQLite.

La vie d’un document

Un agent dépose un rapport hebdomadaire, un client le lit, un collègue corrige un paragraphe et l’agent récupère les retours.

  1. Claude Code appelle create_document via MCP.
  2. Le core vérifie que Jon, qui a connecté l’agent, est éditeur ou propriétaire de l’espace.
  3. Le fichier est écrit dans workspaces/studio/reports/weekly.md.
  4. Git le committe tout de suite, avec l’auteur « Jon via claude-code ».
  5. Un événement arrive dans la boîte de réception des membres, et dans l’e-mail quotidien de ceux qui l’ont activé.
  6. Votre client ouvre la page dans son navigateur, avec un compte ou un lien public.
  7. Un collègue modifie un paragraphe. L’éditeur enregistre deux secondes après la dernière frappe.
  8. La session d’édition devient un seul commit quand il quitte la page, après une minute sans frappe, ou quand quelqu’un d’autre écrit le fichier.
  9. Au passage suivant, l’agent lit les commentaires laissés sur la page avec read_comments.

Ce qui est stocké où

Un seul dossier de données contient tout. Copiez-le et vous avez une sauvegarde.

La base de données

Comptes, sessions, rôles, invitations, jetons d’agent (stockés hachés), liens publics et événements. Aussi l’index de recherche, reconstruit à partir des fichiers à chaque démarrage.

inkmesh.db

Les dépôts git

Un par espace de travail : les fichiers Markdown, leurs images et les fils de commentaires dans .inkmesh/comments/. Vous pouvez les cloner et les lire sans inkmesh.

workspaces/<slug>/

Ce qui quitte le serveur

Les e-mails, par votre propre serveur SMTP, seulement si vous en configurez un. Le script de sauvegarde facultatif pousse chaque espace vers un dépôt GitHub privé. Aucune mesure d’audience.
